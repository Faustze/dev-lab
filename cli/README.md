# cli

CLI-трекер задач на .NET. Только BCL — без сторонних NuGet-пакетов.

Разбор аргументов, работа с файлами и обработка ошибок написаны вручную, без
обёрток, скрывающих механику. В продуктовом коде здесь стоял бы
`System.CommandLine`; тут он намеренно не используется.

Доменная модель общая с [`todo-app`](https://github.com/Faustze/todo-app) —
та же предметная область, те же сущности.

---

## Модель

```markdown
Task
id # Guid, генерируется программой
title # string, обязательное
status # done | in-progress | cancel
priority # low | middle | high
createdAtUtc # DateTime, генерируется программой
updatedAtUtc # DateTime, генерируется программой
description # string?, опциональное
```

`id`, `createdAtUtc` и `updatedAtUtc` пользователь не вводит никогда — их
проставляет программа.

---

## Команды

```
task add <текст> [--priority=low|middle|high]
task list [--all]
task done <id>
task rm <id>
```

| Команда | Поведение                                                                                                                                  |
| ------- | ------------------------------------------------------------------------------------------------------------------------------------------ |
| `add`   | Создаёт задачу. `--priority` опционален, по умолчанию `middle` — среднее из трёх, не искажает сортировку при массовом добавлении без флага |
| `list`  | Без флага — только `in-progress`. С `--all` — все задачи                                                                                   |
| `done`  | Переводит задачу в статус `done`                                                                                                           |
| `rm`    | Удаляет задачу                                                                                                                             |

Вывод `list`:

```
3f2a8b1c  Купить хлеб            high
9d4e7f02  Позвонить в банк       middle
```

---

## Решения

### Идентификатор — короткий префикс `Guid`

В командах задача указывается началом `id`, по образцу коротких SHA в git:
`task done 3f2a8b1c`.

**Длина префикса — минимальная однозначная, а не фиксированная.** Принимается
любой префикс, который совпадает ровно с одной задачей. `list` печатает
столько символов, сколько нужно, чтобы все показанные идентификаторы
различались, — поэтому по мере роста числа задач вывод удлиняется сам.

Фиксированные 8 символов были бы проще, но пришлось бы выбирать длину
наугад: слишком короткая упирается в коллизии, слишком длинная неудобна для
набора. Минимальная однозначная снимает выбор — длина следует из данных.

**Отвергнутая альтернатива — порядковый номер строки в выводе `list`.** Она
выглядит удобнее, но хрупкая: `list` и `list --all` печатают разные наборы, а
процесс между запусками ничего не помнит и не может знать, от какого списка
пользователь отсчитывал. `done 3` молча отметил бы не ту задачу. Номер также
поехал бы после каждого удаления.

Префикс `Guid` стабилен всегда: не зависит ни от фильтра, ни от порядка вывода,
ни от удалений.

Цена решения — два случая ошибки, которые надо обработать явно:

| Случай                               | Поведение                                                                         |
| ------------------------------------ | --------------------------------------------------------------------------------- |
| Префикс не совпал ни с одной задачей | Ошибка «задача не найдена», ненулевой код возврата                                |
| Префикс совпал с несколькими         | Ошибка «неоднозначный идентификатор» со списком совпавших, ненулевой код возврата |

Второй случай — прямой аналог `ambiguous argument` в git.

### Порядок вывода фиксирован

`list` сортирует по `createdAtUtc` по возрастанию. Порядок задан явно и
одинаков для всех команд, чтобы вывод был воспроизводим.

### `status` не задаётся при создании

Новая задача всегда `in-progress`. Флага `--status` у `add` нет: создать сразу
завершённую или отменённую задачу бессмысленно. Смена статуса — отдельная
операция (`done`).

Это согласовано с `todo-app`, где `CreateTask` не содержит поля `status`, а
`create()` проставляет `in-progress` жёстко.

### Аргументы команд выведены из CRUD-типов

`add` принимает подмножество полей `CreateTask`, будущий `edit` будет принимать
подмножество `UpdateTask`. Поля, которых нет в этих типах, через командную
строку не задаются.

## Вне текущего объёма

Отложено сознательно. Записано, чтобы позже отличать решение от забывчивости.

| Что                                           | Почему отложено                                                                                                                                                                                                                                                     | Когда вернуть                                                                |
| --------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------- |
| **Теги**                                      | Тег — отдельная сущность `TaskTag {id, name, color}`, а `CreateTask` хранит `tagId`, не имя. Тянет вторую коллекцию в хранилище, команды `tag add/list/rm`, решение про автосоздание тега и обязательный `color`. Для одной сущности в одном файле это несоразмерно | Вместе с переходом на БД, где связь «задача → тег» становится внешним ключом |
| **`edit`**                                    | Частичное обновление требует отличать «поле не передали» от «поле обнулили» — `UpdateTask` это `Partial<...>`. Тема самостоятельная и к базовым командам ортогональная                                                                                              | После того как основные команды готовы                                       |
| **`--description`**                           | Длинный текст в аргументе командной строки неудобен и ничего не добавляет к механике                                                                                                                                                                                | Вместе с `edit` либо никогда                                                 |
| **Фильтры и пагинация в `list`**              | Один флаг `--all` покрывает потребность на текущем объёме данных. Полноценная фильтрация имеет смысл там, где её выполняет БД                                                                                                                                       | Вместе с переходом на БД                                                     |
| **`System.CommandLine` и любые NuGet-пакеты** | Ручной разбор аргументов здесь — цель, а не издержка                                                                                                                                                                                                                | Не возвращать в этом проекте                                                 |

## Хранение

Задачи лежат в JSON-файле. Между запусками программы состояние существует
только там: процесс завершается после каждой команды, память освобождается.

## Открытые вопросы

Сгруппированы по тому, что именно они блокируют.

### Нужно решить до первой записи в файл

- [ ] Форма JSON: голый массив задач или объект с полем версии схемы
- [ ] Поведение при отсутствующем файле: создать пустой или сообщить об ошибке

### Нужно решить до обработки ошибок

- [ ] Поведение при повреждённом JSON: что видит пользователь и теряются ли данные
- [ ] Конкретные коды возврата. Решено только, что успех — `0`, а каждый класс ошибки получает своё ненулевое значение

### Сознательно отложено

- [ ] **Путь и имя файла хранилища.** Рядом с бинарником, в `$XDG_DATA_HOME`, или через переменную окружения. Решение зависит от соглашений о размещении данных в Unix; до тех пор — файл рядом с бинарником, замена в одну строку
