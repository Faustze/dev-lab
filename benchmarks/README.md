# benchmarks

Замеры производительности. Формат единый для всех.

## Требования к замеру

1. **Одна папка — один вопрос.** Не «потестил сервис», а «как меняется p99
   при росте конкурентности с 10 до 200 при пуле соединений в 20».
2. **Окружение указывается всегда** — ядра, память, ОС, версия Go, где
   выполнялось (локально / VPS / облако и тариф). Без этого цифры
   не сопоставимы ни с чем.
3. **Методика до результата** — чем нагружал, сколько прогонов, сколько
   прогревочных, как считался разброс.
4. **Сырые данные в репозитории** — `results.csv` рядом со скриптом.
5. **Гипотеза записывается до прогона.** Записанная задним числом обесценивает
   замер.
6. **Вывод отдельным пунктом** — что число означает.
7. **Отрицательный результат публикуется** инженерной формулировкой:
   «упёрлось в пул соединений, а не в CPU», а не «не получилось».

## Именование

`NNN-краткое-описание/` — трёхзначный номер по порядку.

```
benchmarks/
└── 003-pool-size-vs-p99/
    ├── README.md      # вопрос → окружение → методика → результаты → вывод
    ├── run.sh         # воспроизводимый запуск
    └── results.csv    # сырые данные
```

## Метрики

| Метрика | Определение |
|---|---|
| **RPS** | успешных запросов в секунду при заданной конкурентности |
| **p50 / p95 / p99** | латентность по перцентилям. **Среднее как главная метрика не принимается** — оно скрывает хвост |
| **RSS** | резидентная память процесса: в покое и под нагрузкой |
| **Аллокации** | из `pprof`: сколько и где выделяется |
| **Время запроса** | до и после индекса — для оптимизаций базы |
| **Размер образа / время сборки / время выката** | для контейнеризации |
| **Время обнаружения** | сколько прошло от поломки до срабатывания алерта |
| **Потери при отказе** | сколько запросов теряется, когда падает зависимость |

Один запуск — не замер. Всегда фиксируется число прогонов и прогревочные.
